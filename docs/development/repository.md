## 分支与评审

日常工作使用短期功能分支，PR 对应一个清晰目标。改动公共格式、协议、持久化、输入权限或发行方式时附设计决定；较小实现选择留在 PR 即可。

审查基于当前差异、所关联需求及实际检查。合并前重新核对目标分支，解决语义冲突；不能只接受文本自动合并结果。需要临时例外时记录影响、期限、替代检查和具备相应权限的决定人。

主分支规则没有绕过名单；合并方式为 squash，自动合并关闭。PR 标题和说明作为最终提交标题与正文，合并后删除已完成的开发分支。依赖漏洞通知和安全更新已启用，Python 与 GitHub Actions 依赖按周检查。

## 持续集成

[文档工作流](../../.github/workflows/docs.yml)在 pull_request、main 推送和手动触发时执行。令牌只有 contents:read；checkout 不保留凭据；Action 固定完整提交摘要。

外部 PR 不取得签名、发布或模型连接秘密，不使用 pull_request_target 执行贡献分支代码。文档工作流只解析和验证资料，不发布制品。工作流同时运行原型页面与交互检查。[Engine 工作流](../../.github/workflows/engine.yml)运行锁定依赖安装、代码检查、单元与集成测试、构建及 wheel 安装示例。应用组件建立后按受影响范围增加类型、模型、原生和安装检查，必需检查名称保持可识别。

依赖更新检查锁文件、许可和目标平台。自动更新 PR 与普通贡献接受同样审查；缓存和构建工件按来源权限隔离。

## 问题与讨论

缺陷、功能和设计分别使用 Issue 表单。维护者确认复现输入、影响范围、需求关联、优先级和完成判据后再安排实施。重复问题链接原项并说明新增材料；含秘密或漏洞细节时转为私密处理。

Issue 关闭依据实际解决结果或有权作出的范围决定，发布后跟进目标平台反馈。

## 发行与维护

公开文档、契约检查、兼容范围与发行内容按同一版本维护。

设计文档版本和应用版本独立。应用使用语义化版本；破坏性格式与接口变化还要更新对应协议或格式版本。未发布的源码与文档变更写入 CHANGELOG 的 Unreleased。

稳定版按[发行设计](../operations/release.md)生成新标签、摘要、签名、SBOM 和兼容矩阵。稳定版通过支持平台的安装、更新和恢复测试后发布。撤回有缺陷制品时保留历史说明和恢复入口，修复以新版本发布。

维护与安全报告入口见[维护职责](../../GOVERNANCE.md)和[安全报告](../../SECURITY.md)。应用版本的支持范围随发行记录维护。
