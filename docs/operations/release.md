# 构建、安装、发行与恢复

## 支持矩阵

| 对象 | 首期目标 |
|---|---|
| Windows | Windows 11 x64；Windows 10 x64 的指定构建与 WebView2 组合 |
| macOS | macOS 14 起的指定系统组合；arm64 / x64 独立制品与 WKWebView |
| Linux | Ubuntu 24.04 构建基线；x64 / arm64；X11 与具体 Wayland 合成器、Portal、WebKitGTK 组合分别验收 |
| 宿主 | Tauri 2.12、React 19.3、TypeScript，精确补丁锁定 |
| Agent | Rust，满足宿主与 crate 的工具链要求 |
| Engine | CPython 3.12+，发行固定解释器和 SQLite |
| MCP | 2026-07-28 主协议与 2025-11-25 兼容；默认 stdio、显式 Streamable HTTP，旧 HTTP+SSE 独立启用 |

每版公布准确系统构建、架构、WebView、原生后端、显示服务/合成器、协议与格式矩阵。全部显示屏录制与 Portal 控制分别标明实际验收能力；原生规则见[跨平台架构](../architecture/platforms.md)。

## 构建与制品

前端保存 pnpm 锁，Rust 保存 Cargo.lock、工具链、target 和 features，Python 保存完整依赖锁。

每个 OS/架构分别构建 Studio、Engine、Agent、Bridge 的兼容组合，检查本平台原生库、Python 扩展和资源布局。安装用户不需要 Python。

PR、候选构建和签名发行隔离。外部贡献没有发行秘密和写入令牌；缓存与工件按信任来源区分。不能直接把外部 PR 工件提升为可信发行。

发行清单绑定源码提交、锁摘要、组件版本、平台、制品摘要、签名和 SBOM。实际二进制清单覆盖嵌入依赖，不用源码依赖表替代。已发行标签和制品不覆盖；修复使用新版本。

## 安装

Windows 提供每用户安装和包含 WebView2 资源的离线安装。macOS 提供签名、公证的应用包与 DMG；Linux 按自包含 AppImage 或已选择的包管理器渠道安装，并核对系统库基线。程序目录和工作空间分离；个人任务、截图、凭据不进入安装包。

各平台干净机覆盖无 Python、WebView/系统库依赖、普通账户、中文及 Unicode 路径、空间不足、代理失败、权限拒绝和重启。失败给出具体依赖与恢复入口。

## 更新协调

1. 下载到隔离目录，核对期望发布者、版本、签名和字节摘要。
2. 检查全部 Engine、Agent、Bridge 和其他会话，停止接收新运行。
3. 确认草稿持久化、运行收拢、输入释放和一致备份。
4. 安装新兼容组合，保留前一有效版本。
5. 检查数据读写能力，执行独占迁移并验证。
6. 首次启动完成不发送真实输入的检查后，切换活动版本。

新旧 Agent 不能同时控制桌面。更新签名、Windows 代码签名、macOS Developer ID/公证与 Linux 分发签名分别管理，私钥不随源码或安装包分发。

## 失败与恢复

下载、签名或安装失败保留旧版入口。数据兼容时可直接回退程序；不兼容时恢复到新目录，升级后的编辑与记录继续保留可导出。恢复不重放流程，旧程序不得写入不支持的格式。

卸载默认保留工作空间与备份，删除数据需明确选择具体目录。

## V0.1.0 发行申请

全部设计功能实现、完成对应验收并经仓库所有者授权合并 main 后，方可申请应用 V0.1.0 发行。申请前按[产品需求](../product/requirements.md)、[功能映射](../design/feature-design-map.md)和[需求追踪](../quality/traceability.md)逐项核对实现与验收结果，覆盖工作台、Engine、Desktop Agent、MCP、CLI 及安装更新恢复的完整设计范围。

原型、执行核心或部分里程碑完成均不满足申请条件；尚未实现或未完成验收的设计功能须先完成。各开发分支须完成[独立审查循环](../development/repository.md#分支与评审)。申请时完成下列门禁中的制品准备与验收；发行获批后方可创建正式发行标签并发布制品，发布后核对渠道中的真实下载字节。合并授权不包含发行授权。

## 发行门禁

- 发行包包含 Apache-2.0 的完整 LICENSE，自有包元数据使用 `Apache-2.0`，第三方许可与通知齐全。
- 私密报告入口已启用，并用合成报告验证接收。
- 支持矩阵的安装、运行、急停、升级与恢复通过。
- 许可、二进制 SBOM、摘要、签名对应同一制品。
- README、操作说明和变更记录与实际版本一致。
- 发行者核对渠道中的真实下载字节和发布权限。

## 更新资料与签名字节

[更新契约](../../contracts/updates.schema.json)定义 root、release、revocations 三种 signed 对象及 signatures 信封。未知字段、重复 JSON 键、非整数数字、不合法 UTF-8、孤立代理码点和超过 1MiB 的资料在验签前拒绝。所有属性名为 Schema 中列出的 ASCII 名称；数值限 0..9007199254740991。

签名字节为 UTF-8 的 `DeskWeaveStudio/update/v1\n`、signed.role、一个 LF，再拼接 signed 的规范 JSON；不含 BOM、签名数组或结尾换行。规范 JSON 递归按 ASCII 属性名升序排列对象键，数组保持顺序；不含空格。整数使用十进制最短表示，不接受负零、小数或指数。字符串转义双引号与反斜杠，退格/换页/换行/回车/制表分别使用 `\b`、`\f`、`\n`、`\r`、`\t`，其他 U+0000..001F 使用小写 `\u00xx`；斜杠和其余 Unicode 标量不转义，直接编码 UTF-8。跨语言必须重建完全相同字节。

算法固定 Ed25519，publicKey 为 32 字节原始公钥的标准带填充 Base64；keyId 为这 32 字节的 SHA-256 小写十六进制。signature 为上述签名字节的 64 字节签名的标准带填充 Base64。keyId 必须与公钥重算一致；同一 keyId 的多份签名只计一次，未知、重复或不合法签名不增加票数。禁止按签名输入自行选择其他算法。

release 固定 product、rootVersion、channel、单调 sequence、展示 version、issuedAt/expiresAt 和唯一平台 artifact。artifact 绑定下载 HTTPS URL、真实长度/摘要、对应平台发行身份、四组件版本、协议和可读写工作空间格式；下载跳转仍须 HTTPS，跨主机只接受发行客户端预置的下载源白名单。每次实际安装重新核对消费字节及对应平台签名/受信分发渠道，不能只信下载缓存名或文件路径。展示版本不参与防重放排序。

## 初始可信根、通道与持久信任状态

发行二进制嵌入已批准的 root 信封、其摘要、当前安装 release 身份和初始 revocations；网络返回的自签根不能替换这个锚。root 以离线 3 把根密钥中的 2 把签名，stable 与 preview 分别委派至少一把在线发布密钥，各自阈值至少 1；根角色与在线发布键不重叠，同一在线密钥不跨通道使用。各平台代码与分发签名密钥独立保存。通道切换由本地用户设置明确选择，网络响应不能自动改通道或凭预览版展示版本进入稳定通道。

用户应用数据区保存 trustState：generation、rootVersion/摘要、rootHistory、revocationsVersion/摘要、每通道最高 sequence/相应清单摘要、lastTrustedTime。它不位于工作空间，不参加工作空间恢复或程序版本回退。单用户更新协调器在锁内原子更新状态和原请求记录，保留最近有效副本；已接受的同序号只能对应相同规范 signed 摘要。较小序号拒绝；相同序号的相同清单可继续原安装，但不能当作新发行。通道各自推进，不以 stable 的序号比较 preview。

rootHistory 按版本顺序保存从安装内置根锚到当前根的完整 (version, sha256) 引用。每份原始 root 签名信封以其规范 signed 摘要封存到用户级更新对象区，先刷新文件，再原子提交包含链引用的 trustState；rootHistory 的每一项均对应可验签的 root 原件，当前根引用位于链尾。已接受的吊销原件也按状态摘要保留，后续检查用其验证累积集合未减少。这些对象不随工作空间恢复或旧程序替换删除。

每次启动和更新检查先从安装二进制内置锚重新核对所保存链的摘要、逐版版本连续性、旧根/新根双阈值签名、委派分离和最低安全序号；从已验证的每一版链恢复历史在线与根角色密钥集合。历史根只用于重建已接受的信任关系，不因其如今过期而抹除历史委派；当前根仍按本次时间检查有效期，新收到根则在接受时检查其有效期。缺失、篡改或无法重验任一历史链节点时返回信任资料不可用，恢复已验证原件或使用受信完整安装包修复，不能把未知 keyId 加入历史集合来继续。

累积 revokedKeyIds 的成员资格依据上述完整已验证链判定；已经退出当前委派的旧在线键仍是可识别的历史发布键，并继续保持已撤销状态。未登记在已验签根链通道委派中的键必须拒绝；曾属于根角色的键也不能经此列表吊销。根轮换后的第二次启动使用已保存链重建相同集合，不能因为本轮没有 rootUpdates 就丢失旧委派。

初始通道计数至少为本安装签名清单的序号；其他通道从内置的最低安全序号开始。root 和 revocations 的版本严格单调，最低安全序号只能提高。验签、期限、吊销和通道检查全部通过后才持久化新的最高信任状态；下载或安装失败不降低它。程序回退继续读取较新的信任状态。

root 有效期最多 180 天，release 最多 7 天，revocations 最多 24 小时，均要求 expiresAt>issuedAt。新资料的 issuedAt 不得晚于有效当前时间 5 分钟。有效当前时间取系统 UTC 与 lastTrustedTime 较大者；系统时间倒退超过 5 分钟时停止新更新并要求修正时钟。服务端 Date 头不能延长签名期限。资料过期、缺失或状态损坏时现有已安装应用仍可运行；新安装不得忽略检查，使用重新签发的有效资料或已验证的新完整安装包恢复。信任状态缺失或无法核定时禁止静默归零，通过受信完整安装包和原有效状态恢复。

## 密钥轮换、吊销与失陷恢复

根轮换逐版本取链：root N+1 的同一签名字节必须同时满足旧根 N 的 root 阈值和新根 N+1 自身 root 阈值；先核对版本恰好加 1、期限、keyId 和委派完整性，再提交。缺中间根不能跳过；新根不能降低既有最低安全序号。根私钥分开离线保存，签名发行任务只能接触当前通道的在线发布密钥。

在线发布密钥轮换通过已验证的新 root 增加新 keyId，再发布使用新键的通道清单，最后由新 root 移除旧委派；客户端在每次检查和安装前先更新根及 revocations，再验证 release。revocations 由当前可信根的 root 阈值签名，列出累积 revokedKeyIds、revokedArtifacts 和每通道最低安全序号；revokedKeyIds 只允许可信根链曾登记的在线通道发布键，不允许根角色密钥。根键必须由已验证的新根移除，吊销资料不能反向改变自身验签票数；版本加 1，不能撤回既有吊销或降低门槛。被吊销密钥的签名即使曾在缓存中验证也不再有效，被吊销制品不能继续安装；当前安装受影响时显示具体版本及有效修复入口，不自动执行流程。

发布密钥失陷时由离线根签发新 root 与吊销资料，清除对应下载缓存的安装资格并发布新清单。根阈值失陷或无法收集足够旧根签名时，暂停自动更新，改用项目发行渠道提供、由独立平台签名或受信分发渠道核验的完整安装包重新建立信任。该操作不删除工作空间与有效草稿。

## 人工降级边界与界面

普通更新拒绝降低通道 sequence。人工降级只从可信本地入口发起：目标仍需当前可信根委派的有效 release、最新有效 revocations、正确的平台发行身份和实际字节摘要，且 sequence 不低于最低安全序号，不能使用已吊销版本。历史 release 过期时必须由发行方为该制品重新提供当前有效签名资料；本地确认不能豁免验签或吊销。

确认前展示来源/目标版本、通道、数据读写兼容结果和一致备份位置。Host 签发绑定源版本、目标摘要/序号、root/revocations 版本和备份身份的一次性本地确认，最多 10 分钟；切换版本前重新验证同一计划。确认不经 MCP 或通用设置传入，不降低持久最高序号，也不把下一次自动更新的基线改成旧程序版本。数据不兼容时沿既有恢复到新目录方案执行，不能覆盖当前工作空间。

更新界面以检查、校验、下载、准备、安装、完成/失败呈现实际阶段。签名无效、资料过期、序号回退、制品吊销、时钟异常分别显示对应原因与重试、校正时间或获取有效安装包操作。正常根轮换在验证链完成后继续原流程；缺链或阈值不满足时阻止安装，不能让用户点击“仍然信任”绕过。通道选择与人工降级各保留独立确认状态。

## 平台制品身份

artifact.platform 取 windows-x64、macos-x64、macos-arm64、linux-x64 或 linux-arm64；选择制品时精确匹配 OS、架构和安装渠道。publisher 分别核对 Windows 签名发布者、macOS 固定 Team ID、Linux 受信渠道签名密钥指纹；声明字符串不能替代签名验证。

macOS 对应用及内嵌组件进行一致签名、公证与票据处理；Linux 包管理器安装使用原渠道更新，自包含安装使用对应签名更新包。切换渠道经本地明确操作，不覆盖另一渠道管理的文件。安装后重验四组件、本机通信、权限状态、原生输入清理及工作空间读写。
